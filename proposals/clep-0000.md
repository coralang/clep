## Abstract

A Cora Language Enhancement Proposal (CLEP) is a formal design document providing information to the community, describing a new feature, or defining its processes. This document outlines the governance model, lifecycle states, and review procedures that regulate changes to the language.

## 1. Governance Model

To ensure predictable, high-quality development, decisions follow a **Consensus-Seeking Architecture Council** model.

- **The Community:** Anyone can write, comment, or provide feedback on an LEP.
- **The Champions:** Members who sponsor external CLEPs, guiding them through the review process.
- **The Council:** A core group of maintainers with final authority over status transitions (Acceptance/Rejection).

---

## 2. The LEP Lifecycle

```text
  [ Draft ] ──> [ Proposed ] ──> [ Accepted ] ──> [ Implemented ]
                     │                  │
                     └──> [ Rejected ]  └──> [ Deferred ]
```

### State Definitions

- **Draft:** An unrefined, work-in-progress idea. Not ready for formal review.
- **Proposed:** A complete architectural design seeking formal community and Council feedback.
- **Accepted:** Approved for core implementation. The syntax and semantics are frozen.
- **Rejected:** Permanently turned down. The rationale is documented in the proposal.
- **Deferred:** Valid concept, but paused due to conflicting priorities or technical blockers.
- **Implemented:** The code is completely merged, tested, and shipped in a stable release.

## 3. Step-by-Step Contribution Workflow

### Step 1: Socialize the Concept

Before writing code or text, open a **GitHub Discussion** or issue to gauge early community interest. This limits wasted engineering effort on fundamentally incompatible ideas.

### Step 2: Submit a Draft Pull Request

1. Fork the repository.
2. Duplicate `templates/clep-template.md` into `proposals/new-your-title.md`.
3. Leave `clep: null`; the workflow assigns the next available four-digit ID and creates `clep-XXXX-title-slug.md`.
4. Set the status field to `Draft`.
5. Open a Pull Request.

### Step 3: Peer & Core Review

Once your proposal text is complete, change the YAML header status to `Proposed` and remove the draft flag from the PR.

- **Review Window:** Every proposal stays open for a mandatory **14-day community comment window**.
- **Revisions:** Authors address syntax and implementation feedback directly in the PR branch.

### Step 4: Resolution & Resolution Rules

The Council reviews the proposal at the close of the comment window. Transitions require a quorum agreement:

- **Consensus:** A silent majority or explicit approval from a majority of active Core Council members.
- **Deadlocks:** Tied votes result in a deferral or rejection unless broken by the designated Benevolent Dictator / Lead Architect.

---

## 4. Successful Review Evaluation Criteria

When reviewing an LEP, the council explicitly scores proposals against these four engineering axioms:

1.  **Backwards Compatibility:** Changes must not silently break existing codebases unless an explicit, automated migration path (codemod) is provided.
2.  **Completeness:** Corner cases, compiler error modes, and runtime type-safety hazards must be thoroughly handled in the text.
3.  **Simplicity:** The feature must fit cleanly into existing cognitive paradigms without introducing convoluted or niche keywords.
4.  **Performance Overheads:** Any introduced syntax must outline clear compilation or runtime trade-offs.
